Централизованное хранение ресурса (Hosted CRS)

Единый инвентарь всех судов на отказоустойчивых серверах СВТР (ЦОД Tier III). Исключение рассинхронизации и двойных продаж за счет ACID-транзакций и блокировок на уровне строк БД.

  • По-сегментная продажа: одно место/каюта продается повторно на разных плечах маршрута (до 20+ пристаней)
  • Динамические агентские квоты: жесткие/мягкие блоки с таймером авто-возврата в общий пул
  • Интерактивные схемы судов: по-палубная детализация (СПК «Метеоры», «Валдаи», водоизмещающий флот, паромы, круизные теплоходы)
  • Поддержка каютных планов любой сложности (люксы, полулюксы, места в купе, плацкарт, сидячие)
  • Репликация в горячем резерве (Active-Active) с RPO=0, RTO<30 сек

Управление доходностью (Revenue Management / RMS)

Математически строгая система максимизации выручки на рейсе. Реализация Serial & Parallel Nesting, динамических триггеров и контролируемого овербукинга на базе статистических моделей.

  • Нестинг (Nesting): вложенное квотирование — высокомаржинальные RBD забирают ресурс низких классов при росте спроса
  • Овербукинг: расчет лимита сверхпродажи по модели No-Show (биномиальное/пуассоновское распределение) с доверительным интервалом 95%
  • Динамические триггеры: пересчет тарифов по глубине продаж (Days Before Departure), загрузке судна, календарю, метеоусловиям
  • Управление фаре-классами (RBD), тарифами, правилами тарификации (FP/RP) через админку
  • А/Б тестирование ценовых стратегий на кластерах судов/маршрутов

  • Интеграция с ГИС ЭПД (ФНС/Минтранс) через операторов ИС ЭПД (СБИС, Диадок, Контур и др.)

Алгоритмическое преимущество: от эвристик к математически обоснованным решениям

Мы не используем «экспертные оценки». Каждый параметр овербукинга, каждый триггер открытия класса — результат работы статистических моделей на исторических данных вашего пароходства.

Serial & Parallel Nesting

  • Serial Nesting: Иерархия классов Y → B → M → H → Q → V. Продажа в Y автоматически уменьшает доступность во всех нижестоящих классах. Гарантирует защиту высокой маржи.
  • Parallel Nesting: Независимые пулы для разных сегментов спроса (например, «Раннее бронирование» vs «Корпоративные тарифы») с возможностью перераспределения остатков по правилам.
  • Bid Price Control: Динамическое пороговое значение (Bid Price) для каждого класса, рассчитываемое через DP (Dynamic Programming) или эвристику EMSR-b, обновляется при каждом запросе доступности.
BidPricek = E[Revenue | Accept Requestk] - E[Revenue | Reject Requestk]
ΔV = V(t, x - ek) - V(t, x)
Открытие класса k ⇔ Farek ≥ BidPricek(t, x)

Управляемый овербукинг (Controlled Overbooking)

  • Моделирование No-Show как Бернуллиевского процесса с параметром p, оцениваемым по скользящему окну (последние 50 рейсов данного маршрута/дня недели/судна).
  • Расчет оптимального лимита L* минимизирующего функцию потерь: Cost(Bumping) * P(Show > Cap) + Cost(Spoilage) * P(Show < Cap).
  • Автоматическое закрытие продаж при достижении Booked = Capacity + L*. Алерты диспетчеру при приближении к лимиту.
L* = argmaxL Σ [P(NS = k) * (RevenueL - Penaltymax(0, k-L))]
P(NS=k) ~ Binomial(n=Booked, p=NoShowRate)
CI 95%: p̂ ± 1.96 * √(p̂(1-p̂)/n)

Мультисегментный инвентарь (Multi-leg)

  • Ресурс (место/каюта) моделируется как временной интервал на графе маршрута.
  • Запрос доступности (Avail) решается как задача поиска пути в графе с ограничениями емкости (Max-Flow / Min-Cut на DAG).
  • Автоматическое освобождение ресурса при высадке (Check-out event) и мгновенная доступность для продажи на_downstream_плечах.

Частые вопросы CTO / Коммерческого директора

Ответы на архитектурные и бизнес-вопросы до начала пилотного проекта

Мы уже имеем кассы, турникеты и валидаторы на причалах. Как происходит интеграция без замены «железа»?

СВТР не поставляет оборудование. Наш API-шлюз интегрируется с любой текущей инфраструктурой через стандартные протоколы:

  • Кассы (АТОЛ, Штрих-М, Эвотор и др.) — протокол ФФД 1.2, драйверы ККТ. Билет = фискальный чек + PDF/E-билет в приложении.
  • Турникеты / Входные группы — интеграция через контроллеры доступа (ZKTeco, IronLogic, Perco) по Wiegand/OSDP/HTTP API. Валидация QR/штрих-кода/НФК билета за <200мс.
  • Портативные терминалы контролеров — наш PWA-офлайн-модуль на Android/iOS (IndexedDB) для проверки посадки без связи. Синхронизация при появлении сети.
  • Существующие сайты/приложения — виджет бронирования (iframe/React-компонент) или Headless API для вашего фронтенда.

Мы предоставляем SDK и Postman-коллекции для ваших интеграторов. Типовое подключение кассы/турникета — 1-2 человеко-дня.

Насколько надежен ваш ЦОД? Что если отключат интернет в регионе пароходства?

ЦОД Tier III (Тиер 3): Два независимых канала питания, N+1 по охлаждению, два вышестоящих провайдера (Ростелеком + МГТС/РТКомм), защита DDoS L3-L7 (Qrator/StormWall). SLA 99.98% — это <105 мин простоя в год, финансово обеспеченные штрафы.

Профиль интернета в регионе: Архитектура Offline-First решает эту проблему радикально:

  1. Кассовый терминал/Планшет контролера кэширует актуальный инвентарь и списки посадки (PWA + Service Workers).
  2. Продажа/Посадка происходят локально. Транзакции пишутся в локальную SQLite/IndexedDB.
  3. При появлении связи — автоматическая синхронизация (Conflict-free Replicated Data Types — CRDTs для счетчиков мест).
  4. Гарантия: двойные продажи невозможны даже при длительном офлайне за счет предварительного резервирования квот на терминал (Quota Allocation).
Как выглядит поэтапное внедрение? Можно ли начать с одного направления/судна?

Да, именно так мы и рекомендуем начать (MVP подход). Типичный план:

  1. Этап 1 (Пилот, 4-6 недель): 1-2 судна, 1 маршрут. Только E-Ticketing (веб + касса) + АЦБПДП. CRM/РМС отключены. Цель: проверить интеграцию с «железом» и госсистемами.
  2. Этап 2 (Масштабирование CRS, 2-3 месяца): Подключение всего флота к Hosted CRS. Включение по-сегментной продажи. Настройка агентских квот для ключевых туроператоров.
  3. Этап 3 (RMS, 1-2 месяца): Настройка классов бронирования (RBD), калибровка No-Show моделей на накопленной статистике. Включение Nesting и Overbooking.
  4. Этап 4 (Грузовой контур, параллельно): Внедрение Cargo модуля, ЭТрН, интеграция с 1С и ГИС ЭПД.

Каждый этап дает измеримый бизнес-эффект. Оплачиваете только включенные модули.

Как обеспечивается работа на грузопассажирских паромах (Ro-Pax) где единый инвентарь: и пассажиры, и фура/авто?

Это ключевой кейс для нашей архитектуры. Единый CRS управляет гетерогенным инвентарем через абстракцию «Ресурс»:

  • Пассажирский ресурс: Места в салонах/каютах (классы RBD, нестинг).
  • Грузовой ресурс: Погонные метры на палубе (длина x ширина), контейнерные слоты (TEU), площадь трюма (м²), дедвейт (т).

При бронировании фуры (Ro-Ro) система списывает погонные метры из палубного пула. При бронировании пассажира — место из салонного пула. Пересечений нет, но есть общие ограничения судна (дедвейт, осадка,.trim). RMS учитывает маржинальность: 1 фура = X руб., 1 пасс = Y руб. Оптимизатор распределяет палубную площадь под максимальную выручку рейса.
